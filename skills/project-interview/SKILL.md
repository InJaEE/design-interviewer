# 프로젝트 심층 면접

먼저 `../../AGENTS.md`, `../../docs/data-contract.md`, `../../docs/terminology.md`와 선택된 면접관 스타일 파일을 읽는다.

포트폴리오에 연결된 프로젝트라면 `../../rubric/evidence-guides/portfolio-story.yaml`을 읽고 자료에 부족한 문제, 실제 기여와 의사결정 과정을 우선 확인한다.

프로젝트의 협업 경험을 깊게 확인해야 하면 `../../rubric/evidence-guides/collaboration.yaml`을 읽는다.

프로젝트에서 AI를 사용했다면 `../../rubric/evidence-guides/ai-assisted-work.yaml`을 읽는다.

실제 사용자, 출시 경험 또는 사업 데이터가 제한적인 프로젝트라면 `../../rubric/evidence-guides/early-career-project.yaml`을 읽는다.

## 범위

포트폴리오가 있으면 자료에서 확인 가능한 사실은 다시 묻지 말고 역할, 판단과 인과관계를 확인한다. 자료가 없으면 지원자가 프로젝트 맥락을 설명하도록 시작한다.

## 질문 흐름

- 문제와 목표
- 지원자의 실제 책임 범위
- 사용자·사업·기술 근거
- 검토한 대안과 트레이드오프
- 핵심 디자인 결정
- 협업과 의견 차이
- 결과 측정과 인과관계
- 실패, 학습과 다시 할 경우의 변화

이 목록은 고정 순서가 아니다. 현재 판단 근거의 부족 정도, 서로 맞지 않는 정보, 직무 중요도와 남은 시간을 바탕으로 다음 질문 하나를 고른다.

협업에서는 누구와 일했는지보다 서로 다른 조건, 함께 사용한 판단 기준, 달라지거나 유지된 결정과 지원자 본인의 역할을 확인한다. 디자인이 바뀌지 않았거나 갈등이 없었다는 이유만으로 낮게 평가하지 않는다.

AI 활용에서는 도구 이름보다 맡긴 작업 범위, 생성 결과를 다시 확인한 과정, 채택하거나 제외한 대안, 최종 판단과 결과에 대한 사람의 책임을 확인한다.

실무 경험이 적은 프로젝트에서는 큰 데이터보다 접근 가능한 근거, 여러 문제 중 선택한 기준, 사실과 가정의 구분, 사용자와 제품 조건 사이의 판단과 다음 검증 계획을 확인한다.

평가에서는 권장 답안이나 점수를 공개하지 않는다. 코칭에서는 답변 후 피드백, 권장 구조, 필요할 때 단계적 힌트를 제공한다. 매 답변 직후 이어하기 정보를 저장한다.
