# 실무 경험이 적은 프로젝트 코칭

학교, 동아리, 공모전, 개인 프로젝트와 채용 과제의 포트폴리오 설명을 개선할 때 사용한다. 실제로 하지 않은 조사, 성과와 비즈니스 조건을 만들어내지 않는다. 여기서 만든 답변은 채용 평가 근거로 사용하지 않는다.

## 설명 흐름

```text
프로젝트에서 주어진 주제와 제약
→ 내가 발견한 문제 후보
→ 우선순위와 선택 기준
→ 처음 세운 가설
→ 접근 가능한 방법으로 확인한 내용
→ 바뀐 판단과 디자인
→ 사용자와 제품 조건 사이의 선택
→ 확인하지 못한 내용과 다음 검증
```

## 데이터와 사용자 접근이 제한된 경우

사용자 수를 늘리거나 수치를 꾸미는 대신 다음을 확인한다.

1. 접근 가능한 대상은 누구였나요?
2. 실제 목표 사용자와 어떤 차이가 있었나요?
3. 무엇을 관찰했고 무엇을 해석했나요?
4. 예상과 달랐던 내용은 무엇이었나요?
5. 결과를 어디까지 믿을 수 있나요?
6. 다음에는 무엇을 확인해야 하나요?

직접 사용자를 만나지 못했다면 기존 연구, 리뷰, 문의 내용, 사용성 점검, 전문가 의견 등 실제로 사용한 대체 근거와 한계를 설명한다.

## 주어진 과제인 경우

과제에서 정한 주제를 자신의 문제 정의처럼 바꾸지 않는다. 주어진 범위 안에서 발견한 문제, 우선순위 기준과 선택한 범위를 구분한다.

## 실제 사업 데이터가 없는 경우

매출과 전환율을 만들지 않는다. 사용자에게 필요한 조건, 제품·운영·기술에 필요하다고 가정한 조건, 실제로 확인한 사실을 구분한다. 실제 서비스라면 확인할 데이터와 방법을 제안한다.

## 피드백 방식

- 과장 없이 구체적으로 드러난 판단
- 사실과 가정이 섞인 부분
- 근거 없이 만든 수치나 조건
- 접근 가능한 범위에서 더 확인할 내용
- 권장 설명 흐름
- 사용자가 자신의 언어로 다시 설명할 기회
